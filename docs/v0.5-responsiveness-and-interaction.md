# landfirst — responsiveness, then the interaction model

## Read this first

**Repo:** `C:\Users\offic\OneDrive - divineenergysolutions.com\Desktop\JM\landfirst`
(GitHub `montjeffrey/landfirst`, currently `v0.4.0`)

**What landfirst is,** in the owner's words: *the tool you open when you have a
large number of worktrees or branches being worked on in parallel and you must
manually review git versioning and commits to cleanly organise the project back
into production.* The operator is acting as project manager over parallel

counterpart is `agent-harness`, a sibling project in the same JM folder that

here, and do not add a second task store.**

and highly interactive and will take levels. Two things follow: the target needs
articulating with him before more surface gets built, and the thing must be fast

## Part 1 — Responsiveness. This is the blocker.

Measured on the reference repo (26 branches, 12 worktrees, 1370 commits):

| operation | time |
|---|--:|
| default window, conflict probes on | **230,901 ms** (~3m 51s) |
| `-all` full topology, probes off | **15,717 ms** |
| small fixture, probes on | 364 ms |

Nothing at four minutes is interactive. Nothing at fifteen seconds is either.

### Root cause, already diagnosed

The Go rewrite (v0.2) ported the analysis but **dropped the entire performance
layer** the earlier Node implementation had. That is the whole problem, and the
fix is largely a port rather than an invention.

**No caching across rebuilds.** Go has one per-build local map (`cherryCache` in
`internal/model/landing.go`). The Node version at tag `v0.1.0-node` had four
persistent SHA-keyed caches — `commitSetCache`, `probeCache`, `measureCache`,
`ancestryCache`. Those took it from 12,364 ms cold to **527 ms warm**, because a
SHA-keyed cache means only the branch that actually moved is recomputed.

```bash
git show v0.1.0-node:src/core.mjs     # the four caches and how they key
git show v0.1.0-node:src/watch.mjs    # the fast pass / probe pass split
```

**No watcher at all.** There is no live update in the Go version; `r` triggers a
full cold rebuild. The Node version watched `refs`, `HEAD`, the index and
worktree registrations under `.git` — never the working tree, so editing files
did not churn the view and `node_modules` could not drown it. Every change ran a
fast pass first (no probes) so the surface moved immediately, then a probe pass
that superseded it.

**The expensive calls, all of which scale with branch count:**

- `git cherry` — once per branch, walks the whole range
- `git merge-tree` — O(pairs), the dominant cost when probing
- `git diff --name-only` — once per branch, twice per fork group
- `git merge-base`, `git rev-list --count` — several per branch

On Windows, process spawn is 10x what it costs on Linux, so call *count* matters
more than the work inside each call. An earlier version of this project spent 7
seconds purely on `merge-base --is-ancestor` spawns until they were replaced
with one `git branch --contains` per branch.

### What to do

1. Port the four SHA-keyed caches. This is the single biggest win and the design
   is proven — read it, do not redesign it.
2. Port the watcher with the fast-pass / probe-pass split, so the panel updates
   as the operator works instead of on demand.
3. Make probing incremental: when one ref moves, re-probe only pairs involving
   that ref.
4. Consider persisting the probe cache under the OS cache dir keyed by SHA pair,
   so a cold start after a restart is not a cold rebuild. **Never** write into
   the user's `.git` — see the traps below.
5. Set a target and hold it with a benchmark: **first paint under 1s, warm
   rebuild under 300ms, full topology under 3s** on the reference repo.

## Part 2 — The interaction model. Assess before building.

### Where the design got to, and why

Three visual designs were rendered against the owner's real data and reviewed
with him. The commit-graph shapes were rejected: **anything organised like
`git log --graph` answers "what happened, in what order", which is not the
question this tool exists for.** His words: it should *never leave me questioning
where the branch lands compared with the other contention points.*

What was chosen and shipped in v0.4.0:

- **Fork-point spine** as the primary view (`topology` tab, now the default).
  The base runs down the page; every branch attaches at the commit it actually
  forked from, so distance down the spine is staleness and branches that left
  together sit together. On the reference repo this immediately exposed 8
  branches sharing one fork point — the group genuinely in contention — with the
  rest as stale forks at increasing depth. No ordering of the commit graph had
  made that visible.
- **Contention redefined.** A raw conflict count conflates two unrelated things,
  and the useless one dominates: measured median 14 files against a maximum of
  203. Branches forked from *different eras* conflict on hundreds of files
  because one carries months of unrelated history — that is drift, and it says
  "rebase", not anything about the code. Branches forked *together* that both
  edited the same file are genuinely fighting. Only the second is drawn: files
  **both** branches changed since their shared fork point. Pairs from different
  fork points are not compared at all.

### What is unfinished, and what he asked for

He selected all four of these; only inspection-adjacent pieces exist.

1. **Inspect** — select a commit or range, see the diff. `delta` is installed and
   configured in `~/.config/lazygit/config.yml`; pipe through it when present.
   **Nothing in the graph is inspectable today.**
2. **Branch and worktree topology** — he named worktrees explicitly, twice. There
   are 12 in the reference repo and they are still only a `⬖` marker and a flat
   list. They should be first-class objects in the topology view.
3. **Rearrange** — cherry-pick, reorder, squash, drop. The consolidation work
   itself.
4. **Compare two points** — pick any two commits, branches or worktrees and see
   the delta directly.

Also outstanding: **contention is inline text, not drawn geometry.** He asked for
the matrix as an overlay on the spine; what shipped is the informational half.

### How to run the assessment

Do not guess at the interaction model. Show him rendered candidates built from
his own repository — that is what worked before. Three designs were mocked with
real data and he picked decisively; describing them in prose had not worked.

Questions worth resolving with him, in this order:

- What does a consolidation session actually look like start to finish? The tool
  should follow that shape rather than expose git verbs.
- When two branches contend, what does he want to *do* about it in the moment?
  That decides whether rearrange is cherry-pick-driven or rebase-driven.
- Should worktrees be a lane on the spine, a column, or a separate plane?
- Where does the diff live — a pane, a full-screen mode, or an external pager?
- How many levels deep should selection go: branch, commit, file, hunk?

## Traps already found. Do not rediscover these.

- **`git cherry`, not `rev-list`, for "has this landed".** Comparing commit
  hashes is wrong: a squash-merged branch or one forked before a history rewrite
  reports every post-fork commit as missing. On the reference repo that read as
  *2073 unlanded commits across 17 branches*; the patch-id answer was *45 across
  8*, and three "lost agent branches" were ordinary squash-merged PRs.
- **`merge-tree --write-tree` needs git 2.38 and writes objects into the repo.**
  It left 258 unreachable objects in the owner's repo. Probes run with
  `GIT_OBJECT_DIRECTORY` pointed at a temp store, real store as an alternate. On
  older git, fall back to the pre-2.38 form and report unprobeable pairs as
  **unknown**, never clean. There is a test asserting the loose-object count is
  unchanged after repeated probing — do not weaken it.
- **Never write into `.git`.** Reports go to a temp dir. A 600 kB file rewritten
  inside a cloud-synced `.git` causes sync storms; the repo lives in OneDrive.
- **Lane layout properties are load-bearing** (`internal/model/graph.go`). Lanes
  come from branch identity not row position, colour is a hash of the branch
  name, the base owns lane 0 and its whole first-parent spine, commit ordering
  breaks date ties on hash, and the window always contains a continuous trunk
  plus every merge-base. Each exists because a simpler approach visibly failed —
  one measured case moved 7 of 10 commits on a single new commit. Tests enforce
  all of it.
- **Full topology cannot come from the windowed construction at any cap.**
  `--first-parent` skips commits that arrived through a merge and `base..branch`
  is empty for a branch already merged in, so merged history goes invisible.
  Unlimited asks git for everything.
- **Braille sub-pixels are close to square** (`internal/canvas`). Weighting the y
  axis as though they were half-height stretches every node into an ellipse.
- **A cell holds one foreground colour.** Lanes sit three cells apart so each
  owns its column; closer and branch colours start lying.
- **Do not render colour through a styling library in the canvas.** Those detect
  terminal capability from the environment and silently drop colour without a
  tty, so the same canvas rendered differently under test than in use. Write the
  escape directly.
- **Zed's terminal cannot show images.** It is a fork of Alacritty; Sixel and the
  Kitty protocol are both unsupported and the request is open upstream. Sub-cell
  braille is the ceiling in the dock. Do not plan around an image protocol.
- **Windows stores refs as files**, so `< > " : | ? *` are illegal in branch
  names there and test fixtures cannot use them. Commit subjects have no such
  limit and are the better place for hostile-input tests.
- **`go vet` catches the `json:"a,b"` two-fields-one-tag mistake.** It has been
  made twice in this codebase. Run it.

## Constraints

- Go, single static binary, `CGO_ENABLED=0`, cross-compiled to
  windows/darwin/linux on amd64 and arm64 by `.github/workflows/release.yml` on
  any `v*` tag.
- No HTML, no webview, no browser. The owner was explicit.
- Tests build real git repositories, never mocks. `go vet ./...` clean.
- CI covers three OSes plus a pinned ubuntu-22.04 job on git 2.34, which keeps
  the pre-2.38 conflict fallback honest.
- Guarded writes only: the staged action holds the exact argv shown on screen,
  the confirmation bar swallows every other key, and only `push` and
  `branch -d` are ever one-key. Anything that rewrites history is printed, never
  run — an agent may be mid-commit in that worktree. A test enforces this.

## Definition of done for this phase

1. First paint under 1s, warm rebuild under 300ms, full topology under 3s on the
   reference repo, with a benchmark that fails if they regress.
2. Live updating via a watcher, fast pass then probe pass.
3. A written, agreed interaction model for inspect / worktrees / rearrange /
   compare, with rendered candidates reviewed by the owner — not prose.
4. A phased plan for building it, each phase independently shippable.
5. `go vet` and the full suite green on all three OSes and on git 2.34.
