# landfirst v0.3 — the interactive graph

## What landfirst is

**The tool you open when a lot of parallel work has to be reviewed by hand and
driven back into production.**

Many worktrees and branches are in flight at once. Someone has to look at the
actual git versioning and commits, decide what is real, and consolidate it into
a clean main. That person is the operator, and this is their instrument. It is
not an agent-facing tool and not a task tracker.

Two consequences shape every decision below:

- **The operator reads history closely**, so commit-level detail and diffs are
  first-class, not a footnote.
- **The operator acts on what they read**, so the graph is a control surface,
  not a picture.

### What it is not

`agent-harness` (in the same JM folder, actively developed) is the harness layer
that works with AI subscriptions and other LM harnesses to produce consistent
agent outcomes. It owns agent task state, leases, verification receipts and MCP
tools. landfirst does **not** duplicate any of that and must not grow a second
task store. If the two ever connect, it is landfirst reading harness state to
label a branch with the task that produced it — never the reverse.

`agent-board` (same folder) is an unimplemented 2026-07-02 design spec covering
that same agent-state ground. Not landfirst's territory either.

## The task

Add a **commit graph** to the landfirst TUI and make it manipulable. Today the
panel has `landing`, `merge plan`, and `worktrees` tabs. There is no graph, no
diff view, and nothing can be edited from it — so the operator can see verdicts
but cannot do the actual consolidation work. That is the gap, and it is the
original reason this tool exists.

## Where things stand

**v0.2 (current, Go).** A single static binary. `internal/git` shells out to git
with fixed argv slices; `internal/model` produces landing verdicts, worktree
risk, and merge ordering; `internal/tui` is a bubbletea panel. 6 tests in
`internal/model/landing_test.go` build real throwaway repositories. CI runs on
Windows/macOS/Linux plus a pinned ubuntu-22.04 job for git 2.34.

**v0.1 (`v0.1.0-node` tag).** A Node implementation that had the graph. Its lane
layout algorithm is proven and hard-won — **read it before writing a new one**:

```bash
git show v0.1.0-node:src/core.mjs        # layout(), topoSort(), collectCommitSet()
git show v0.1.0-node:src/lanes-text.mjs  # box-drawing renderer for a terminal
git show v0.1.0-node:test/stability.test.mjs
```

Port that algorithm to Go. Do not re-derive it. It survived several wrong
answers and the tests encode why.

## Build this

### 1. Graph tab

A commit graph in the TUI, using box-drawing characters and truecolour lanes,
rendered from the same model the other tabs use.

Non-negotiable properties, all learned the hard way in v0.1:

- **Lanes come from branch identity, not row position.** Each drawn branch gets
  its own lane, assigned in a fixed order. An earlier version assigned lanes in
  commit order and reused them between non-overlapping branches; it was tighter
  but a single new commit moved 7 of 10 commits to different lanes and colours.
  Unusable when it redraws live.
- **Colour is a hash of the branch name.** Never an allocation counter.
- **The base branch owns lane 0** and its first-parent spine stays there. Do not
  let another branch share lane 0 even when row ranges do not overlap.
- **Ordering is a pure function of the commit set.** Break commit-date ties on
  hash, or commits made in the same second reorder between runs.
- **The window always contains a continuous first-parent trunk plus every
  branch's merge-base**, or branches render floating with no visible connection
  to the base. Filling the window by recency across all refs does not guarantee
  this and produced a graph that looked broken on any repo larger than the limit.
- **Cap drawn branches** (v0.1 used 10, preferring branches with worktrees). One
  lane per branch is only affordable with a budget.

Verify with a test that asserts, on a 40+ commit fixture: zero colour churn and
under 10% lane churn after one new commit, and byte-identical output for two
builds with no repository change.

### 2. Diff / comparison view

Select a commit (or two) in the graph and see the diff. Pipe through **`delta`**
when it is on the PATH — it is already installed on this machine and configured
in `~/.config/lazygit/config.yml` — and fall back to `git diff` plain when not.

Support at least: commit vs parent, branch vs base, and any two selected points.

### 3. Manipulation, guarded

From the graph: cherry-pick, revert, create branch here, reset (soft/mixed),
tag, and delete branch.

The v0.2 confirmation model is the contract and must be preserved:

- The staged action holds the **exact argv slice** shown on screen, so what is
  confirmed is what executes.
- The confirmation bar swallows every key except the answer.
- Only operations that add to the remote are ever one-key: `push`, `branch -d`.
  Anything that rewrites history is printed for the user to run, never executed —
  an agent may be mid-commit in that worktree.
- `internal/model/landing_test.go` has `TestRemedyIsNeverUnsafeForAutomaticActions`.
  Extend it; do not weaken it.

Destructive operations (`reset --hard`, `push --force`, history rewrites) must
stay out of the automatic path entirely.

## Traps already found — do not rediscover these

- **`git cherry`, not `rev-list`.** Counting unlanded work by comparing commit
  hashes is wrong: a squash-merged branch or one forked before a history rewrite
  reports every post-fork commit as missing. On the reference repo that read as
  2073 unlanded commits across 17 branches; the patch-id-aware answer was 45
  across 8. Three "lost agent branches" were ordinary squash-merged PRs.
- **`merge-tree --write-tree` needs git 2.38** and *writes tree objects into the
  repository*. v0.1 left 258 unreachable objects in a real repo. Probes must run
  with `GIT_OBJECT_DIRECTORY` pointed at a temp store and the real store as an
  alternate. On older git, fall back to the pre-2.38 form and report unprobeable
  pairs as **unknown** — never as clean.
- **Capture git's stderr.** Anything inherited corrupts the alternate screen.
- **Windows stores refs as files.** `< > " : | ? *` are illegal in branch names
  there, so test fixtures cannot use them. Commit *subjects* have no such limit
  and are the better place for hostile-input tests.
- **Never write into `.git`.** Reports go to a temp directory. A 600 kB file
  rewritten inside a cloud-synced `.git` causes sync storms.
- **A raw control byte in a source file makes git treat it as binary**, silently
  killing diffs and blame. `.gitattributes` pins the source types to text.

## Constraints

- Go, single static binary, `CGO_ENABLED=0`. No HTML, no webview, no browser.
- No new heavy dependencies without a reason; bubbletea + lipgloss are in.
- Cross-compiles to windows/darwin/linux on amd64 and arm64.
- `go vet ./...` clean. Tests build real repositories, never mocks.
- Startup stays fast; v0.2 reads a 29-unit repo in 87 ms.

## Definition of done

1. `landfirst` opens a graph tab that renders the commit graph legibly in a
   docked terminal panel.
2. Selecting commits shows a diff, through `delta` when available.
3. The listed manipulations work, each behind the existing confirmation model.
4. Stability tests pass: zero colour churn, <10% lane churn, identical rebuilds.
5. `go vet` and the full suite pass on all three OSes and on git 2.34.
6. README documents the graph, the diff view, and every action, stating plainly
   which are automatic and which are print-only.
7. Tagged `v0.3.0`; the release workflow publishes the six binaries.

## Context worth knowing

The repository this is built for has ~25 branches and ~12 worktrees spread
across temp directories, a OneDrive-synced folder, and paths nested inside the
main worktree, with several agents committing in parallel. The graph has to stay
readable and stable under exactly that, because it redraws while work is
happening.
